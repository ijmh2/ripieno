Four tasks. Each is independently verifiable, and none needs anything outside the
repository. The repo is at `~/code/multiplayer-agent` (GitHub
`ijmh2/ripieno`, currently **private**). Do not make it public — that is the
owner's action, not this plan's.

**Hard constraints**

- Read and modify the repository only. Do **not** run `railway`, do not connect
  to `*.up.railway.app`, and do not touch any deployed service.
- Commit as `ijmh2 <ijmh2@users.noreply.github.com>`. Never the real address.
- Do not make the repository public and do not publish to any marketplace.
- `npm test` and `npm run typecheck` must pass after every task. The final check
  is a **fresh clone** through `npm ci` — see Verification.

## Task 1 — Identity: `ijmh2` everywhere a real person is named

The owner wants their handle used rather than a personal name. There are 12
occurrences of `Mira Ellery` and ~147 of bare `Mira`.

**A blind find-and-replace will silently destroy the most valuable tests in the
repository. Read this whole section before editing anything.**

`packages/extension/src/addressing.ts` decides which agent answers a message.
`splitLabel()` parses a label like `"Mira Ellery's reviewer"` into owner `mira
hart` and role `reviewer`, and `mentions()` then reasons about the owner's
**first name** separately from the **role word** and from the **@handle**. The
tests in `packages/extension/test/addressing.test.js` exercise exactly those
distinctions — that a bare first name in prose does not route, that a role word
does, that `miras agent` without an apostrophe still matches, that "the
reviewers meeting is at 4" does not.

If you rewrite those fixtures to `"ijmh2's reviewer"`, the owner's first name
becomes identical to the handle, three separate matching paths collapse into
one, and the tests will still **pass** while no longer testing anything. That is
the failure mode this codebase is full of and it must not be introduced here.

So apply this rule:

1. **Where the text refers to the repository's owner** — `docs/provenance.md:20`
   (`Mira Ellery (@ijmh2): …`), any prose in README or docs — use **`ijmh2`**.
2. **Where the name is a fictional room member in an example, fixture, test or
   demo** — keep a *person-shaped* name, because the addressing logic needs a
   first name distinct from a handle to be tested at all. Replace `Mira Ellery` /
   `Mira` with a clearly fictional persona. The pre-publication audit already
   cleared `Sam Whitfield`, `Kate Ellery` and `Alex` as fictional; add one in the
   same register — **`Mira Ellery`** — and use `@mellery` as its handle wherever
   a handle is needed alongside it.
3. Keep the *shape* of every fixture identical: a two-word owner name, an
   apostrophe-possessive label, a distinct role word. If a test asserted
   something about `"mira"` as a first name, the replacement must be a first
   name of similar character (not a handle, not one syllable that collides with
   a role word).

**Prove the tests still discriminate.** For at least three assertions in
`addressing.test.js`, temporarily break the implementation (for example, make
`mentions()` return `true` unconditionally) and confirm the tests fail. Restore
it. If a test passes with the implementation broken, it is no longer testing
anything and you have hit the failure this section exists to prevent. Report
what you tried and what happened.

Also check: `packages/extension/preview/room.html` is a static UI preview full
of these names; `scripts/demo-provenance.js` prints them into the README's
headline demo output, so if you change them there the README block must be
regenerated by actually running `npm run demo:provenance` and pasting the real
output — not edited by hand.

## Task 3 — An agent that is refused must say so

`packages/extension/src/agentHost.ts` handles `joined`, `entry`, `roster` and
`remoteToolReply` in its `onMessage`, and nothing else. Every `{t:"error"}` the
relay sends an agent connection is silently discarded: "invalid or missing room
token", "viewers cannot attach agents to this room", and the rest. It also never
passes `onEvicted` to `RelayClient`, which treats close codes 4000 and 4003 as
terminal — the human connection in `extension.ts` wires that callback and shows
an error with a Rejoin button; the agent path does not.

The result is an agent stuck on "attaching…" forever with no indication why.

**This is now the most likely first-run failure.** Shared relays require GitHub
verification by default as of commit `202f1de`, so refusals are more common than
they were, and refusal is exactly the path that fails silently.

Fix both halves: handle the `error` frame, and wire `onEvicted`. Surface it
where the person can see it — the agent's output channel *and* the tree, so an
agent that will never attach does not present as one that is still trying. Look
at how `extension.ts` handles the same two cases for the human connection and be
consistent with it rather than inventing a second pattern.

Add a test. `packages/extension/test/agentHost.test.js` already drives a real
`AgentHost` against a real relay; a relay configured with a token, joined
without one, is a refusal you can assert on.

## Task 4 — The shared workspace is not a person

`WorkspaceHost.say()` (`packages/workspace-host/src/host.ts:206`) sends a plain
`say` on a `role: "workspace"` connection. `Room.say()`
(`packages/relay/src/room.ts`) special-cases `role === "agent"` and otherwise
falls through to the human path — so the container's own announcements are
appended with `kind: "human"` and no `hops`.

Every member's `AgentHost` then runs `answersEntry`, sees a human message, and
the primary-agent fallback fires. So the container saying "cloned the repository"
wakes every primary agent in the room, each spending a turn on it.

The room already refuses to treat the container as a member elsewhere —
`describeMembers` filters `kind === "workspace"` out of the roster, and there are
tests asserting it is never described to an agent as a person. This is the same
principle, missed on the transcript path.

Give the container's messages a kind that agents do not answer. `system` is the
obvious candidate and needs checking against how the UI renders it and how
`trim()` treats it (system entries are now discarded first when the transcript is
full — make sure a container announcement being evicted early is acceptable, and
say so in the comment if you keep it). Add a test that a workspace-role `say`
wakes nobody.

## Verification

After each task: `npm test` and `npm run typecheck`.

At the end, the only check that has ever caught the real problems here — clone
to a temp directory and follow the README as written:

```bash
git clone ~/code/multiplayer-agent /tmp/ripieno-verify
cd /tmp/ripieno-verify
npm ci          # fails loudly if the lock file drifted
npm test
npm run typecheck
npm run package
```

Three separate bugs in this repository existed **only** for someone cloning
fresh — a missing `vsce` dependency, an unbuilt `relay-client`, and a stale lock
file — and none was visible in a working copy. `npm test` in the working tree
proves nothing about a clone.

Commit each task separately, with a message that says what was wrong and why the
fix is right. Do not squash them. Push to `main`; CI must be green.

## Explicitly not in scope

- **Making the repository public.** Owner's decision.
- **Screenshots.** The product is visual and has none, which is its largest gap
  — but they need a human at a keyboard.
- **Streaming agent output.** The room shows nothing while an agent works, which
  is the single thing that most makes a working product feel broken. It is days
  of work and belongs in its own change.
- **Roster pruning.** `Room.known` is never deleted from, so the roster grows
  forever and now costs tokens every turn. Real, but it touches presence
  semantics and deserves its own change with its own tests.
